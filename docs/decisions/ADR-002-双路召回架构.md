# ADR-002: 双路召回架构（结构化优先 + 语义补充）

## Status: Accepted (2026-09-20)

## Background

产品的心脏是「写前召回」——进入某章时自动把“本章出场人物当前状态 + 未回收伏笔 + 相关历史片段”注入写作上下文，以解决长篇“吃书”。但《01-需求文档》§9 风险登记册明确列为**高风险**：“召回准确性无法在需求阶段保证，中文长文本向量检索效果不稳定”。且存在**降级红线**：未配置模型时全部本地功能必须可用（红线 3），写前召回必须自动触发（红线 1）。

若把召回完全押在向量语义检索上，则：中文长文本检索不稳定 → 召回可能整体失败；未配模型 → 连 embedding 都没有 → 召回面板空白 → 直接违反红线 1 + 红线 3。

## Decision

采用**两路召回，互为补充，结构化优先**：

| 路径 | 类型 | 做法 | 对模型/向量的依赖 |
|---|---|---|---|
| 结构化召回 | 硬 | 按本章出场人物 → 查 `character_state` / `foreshadow`；按大纲涉及的势力/地点 → 查 `world_entry` | **不依赖**向量与模型，命中率确定 |
| 语义召回 | 软 | 用 `recall_query.md` 生成查询 → 向量检索 top-k（k=5，相似度阈值 0.6） | 依赖 embedding 模型（与 LLM） |

两路合并去重，按「**结构化在前、语义在后**」排序注入，注入总量硬上限 4000 字，超出按重要性截断。每次召回写 `recall_log`（含 `structured_hits` / `semantic_hits`）以便调优。

## Consequences

**正面**
- 结构化路径是确定性的：**即使向量检索完全失效，核心的“人物状态 + 未回收伏笔”依然准确送达**——直接对冲 §9 高风险项。
- 无模型时语义路整体跳过，结构化路照常返回，召回面板不空白 → 同时满足红线 1 与红线 3（TC-19）。
- `recall_log` 的双路命中数让“该提醒的没提醒”可定位（是召回未命中还是前端未展示）。
- 向量召回只做增量补充，**不承担主要责任**，换 embedding 模型的风险被隔离在软路径。

**负面 / 代价**
- 两路合并去重、分级排序、预算截断的逻辑更复杂（`recall_service` 是复杂度集中点）。
- 语义路径引入对 Ollama/embedding provider 的可选依赖（无则少一路，非阻断）。
- 需要一张 `recall_log` 表并保持其数据质量（见“召回 GET 有写副作用”的坑）。
